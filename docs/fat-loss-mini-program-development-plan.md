# 减脂打卡微信小程序：开发计划与质量验收标准

> 状态：持续维护  
> 版本：v0.1  
> 最后更新：2026-09-01

## 1. 产品范围与已确认决策

产品定位为清新、轻盈、简约且带有趣味感的个人减脂记录工具。它帮助用户建立档案，完成早/中/晚餐、运动与放纵餐打卡，沉淀图片和文字记录，并通过体重、BMI、估算体脂率、热量及趋势图提供可理解的数据反馈。

- 使用微信登录与微信云开发；用户档案、打卡图片和记录均持久化保存。
- 首次建档收集性别、年龄、身高、初始体重、目标体重和目标日期。
- 餐食首版采用“分类 + 份量 + 自动估算热量 + 可手动修改”。不在首版承诺由照片直接识别热量。
- BMI 自动计算；体脂率为基于性别、年龄、BMI、体重等数据的**估算值**，页面必须明确说明其仅供趋势参考、不能替代医疗或专业体脂设备。
- 底部导航固定为：首页、记录、数据、我的。
- 用户达成目标体重后，可以生成可保存、可分享的达标海报。

## 2. 实施路线与交付物

### 阶段 A：设计审计与视觉基线

1. 读取 `UI ref/` 高保真原型，建立页面、状态与交互清单。
2. 审核 `design/` 拆分组件，记录文件格式、透明度、可用尺寸、适配边界和版权/来源状态。
3. 输出颜色、字号、字重、圆角、阴影、间距、动效与插画风格规范。
4. 建立“原型 → 页面 → 组件 → 资产”映射表，并标注缺失资产。

交付物：设计审计表、设计令牌、组件清单、资产缺口清单。

### 阶段 B：工程与云开发基础

1. 建立原生微信小程序工程、全局主题、页面路由、TabBar 和通用错误处理。
2. 配置云环境、云数据库、云存储与云函数；不将任何密钥写入客户端代码。
3. 建立登录身份关联、统一数据访问层、上传压缩/重试工具、加载/空态/错误态组件。
4. 定义并实现数据集合：`users`、`body_records`、`checkins`、`daily_summary`、`posters`。
5. 配置按用户身份隔离的数据库与存储权限。

交付物：可登录、可建档、可安全读写个人数据的基础版本。

### 阶段 C：首次建档与首页

1. 完成资料填写、校验、BMI 和估算体脂率计算与保存。
2. 首页展示今日餐食、运动、放纵餐状态，以及当前体重、目标进度、连续打卡和日汇总。
3. 使用 Banner 展示可个性化的提醒：目标进度、坚持鼓励、数据变化和成就，而非假设所有用户有同一种减脂动机或节奏。

交付物：用户在一次首次使用中完成建档并看懂今日下一步。

### 阶段 D：记录闭环

1. 餐食：类别、份量、估算热量、手动调整、文字备注、多图上传与查看。
2. 运动：类型、时长、强度/消耗、备注与图片。
3. 身体数据：按日期记录体重，自动更新 BMI 与估算体脂率，支持历史查看和可控修改。
4. 放纵餐：以不羞辱、不过度限制的中性语言记录，避免负面惩罚设计。

交付物：每个打卡流程保持“选类型 → 填写/上传 → 保存”的低摩擦路径，记录即时同步至云端。

### 阶段 E：数据洞察与达标海报

1. 实现体重、BMI、估算体脂率曲线，并支持日/周/月切换。
2. 展示起始、当前、目标、差距、打卡完成率和连续天数。
3. 仅以用户实际数据生成描述性反馈，避免医疗结论、极端热量建议或未经证实的预测。
4. 目标达成后，以 Canvas 生成高清个人海报，支持预览与保存至相册。

交付物：完整的数据看板与可分享的达标激励闭环。

### 阶段 F：质量、隐私与真机发布准备

1. 覆盖空数据、重复提交、上传失败、网络切换、跨日、权限拒绝、日期回填等边界情形。
2. 完成多屏幕真机测试、性能测试、云权限审计与隐私文案。
3. 对照本文件第 5 节逐项验收，遗留问题分级后闭环。

## 3. 视觉资产与 imagegen 策略

### 3.1 优先级

1. 优先复用 `design/` 中符合规范的原始组件。
2. 简单图形、布局、按钮、进度环、曲线和常规图标优先使用代码、Canvas 或已有矢量资产实现。
3. 现有分层素材允许裁切、留白调整、等比缩放和容器适配；**严禁为填满容器而非等比拉伸、压扁、低清放大或破坏图层关系。**
4. 当素材分辨率、构图、透明边缘、风格或尺寸无法满足页面适配时，使用 imagegen 生成新的替代资产；不得以失真的旧素材勉强上线。

### 3.2 批量素材板策略

为减少生成次数，按“同一视觉语言、同一用途”生成单张素材板，后续拆分并逐项质检。素材板使用统一暖米白背景 `#F7F2E9`（如需直接用于界面则要求真实透明背景），元素之间保留至少一个元素宽度的间隔；无文字、无水印、无边框、无重叠。

- 餐食素材板：早餐、轻食、水果、蛋白质、主食、甜品、火锅等。
- 运动素材板：跑步、跳绳、骑行、力量、瑜伽、游泳、拉伸等。
- 状态与成就素材板：空状态、打卡成功、连续打卡、目标接近、达标庆祝。
- Banner 插画板：首页欢迎、数据趋势、日常坚持、目标达成。
- 海报装饰素材板：花朵、叶片、星星、奖章、彩带、趣味角色等。

每次生成前记录用途、素材板构成、尺寸、背景、参考图角色、必须保持项和禁止项；生成后检查风格、边缘、透明度、裁切安全区和真机清晰度。项目引用的最终资产必须复制到工作区并采用版本化文件名，不能仅引用工具默认目录。

### 3.3 生成标准

- 风格：清新、轻盈、简约、可爱；同批及跨批资产在色相、描边、阴影和拟物程度上保持一致。
- 适配：关键主体留在安全区内；在常见小程序尺寸与 1x/2x/3x DPR 下不被裁断、不模糊。
- 可访问性：插画不承载唯一关键信息；所有状态仍有文字或图标说明。
- 多元与尊重：人物/角色不默认单一体型、性别气质、年龄、肤色或运动能力；不制造体型羞耻，也不将单一减重速度定义为成功。

## 4. 持续维护规则

- 每次范围、设计、数据结构或验收口径变更后，同步更新本文件的版本、日期和相关章节。
- 原型、实现和验收不一致时，以产品负责人最新确认的决策为准，并记录差异与处理结果。
- 新增资产必须在资产清单中记录来源（现有设计、代码绘制或 imagegen）、版本、用途和替换关系。
- 未通过高风险验收项的功能不得标记为完成。

## 5. 高标准验收标准

### 5.1 功能正确性

- 登录、建档、餐食/运动/放纵餐/身体数据记录、图片上传、云端读取、趋势图与海报流程在真机上全部可完成，无阻塞、无数据串用户、无重复写入。
- 所有字段都有符合业务含义的必填、范围与格式校验；校验提示具体、礼貌且可恢复。
- 热量估算展示依据（类别与份量），用户修改后以修改值为准且可追溯。
- BMI 计算精确、显示规则一致；估算体脂率始终附带“估算/仅供参考”说明。
- 历史编辑和删除行为有明确反馈，聚合数据与图表在操作后正确刷新。

### 5.2 视觉与图片质量（发布阻断级）

- 与已确认高保真原型在色彩、层级、字号、间距、圆角、阴影、插画摆放和状态反馈上保持高度一致；任何未被确认的视觉偏差均不得作为最终稿。
- 所有图片在目标容器内保持正确比例，无拉伸、锯齿、异常裁切、透明边缘脏边、色块、压缩伪影或可见水印。
- 每一张图片在 iPhone 与 Android 常见分辨率、深浅背景、1x/2x/3x 显示密度下人工检查；关键视觉素材必须清晰且留有安全边距。
- 同页所有插画的笔触、光源、阴影方向、饱和度、线宽和拟物程度一致；不同来源的素材若视觉冲突，必须替换或重新生成。
- 图像上传、加载、失败、重试和空态均有精致且不跳动的界面；不得出现白块、布局坍塌、图片闪烁或占位符长期滞留。
- 海报输出清晰，关键信息不会被头像、刘海屏安全区或裁切遮挡；保存预览与最终文件一致。

### 5.3 流畅度与稳定性（发布阻断级）

- 页面首次可交互、Tab 切换、表单打开、保存反馈和图片预览均应主观流畅，无可感知卡顿、掉帧或无响应。
- 所有异步操作都具备防重复提交、加载态、超时/失败提示和可重试路径；网络波动不能导致界面永久卡死或数据状态不明。
- 大图在上传前压缩并显示进度；列表和图表不能因历史记录增长而明显掉帧。
- 连续快速点击、返回、切换 Tab、杀进程重进、弱网重连均不能导致崩溃、重复数据或错乱状态。
- 发布前在至少一台 iOS 与一台 Android 真机完成核心流程回归；任何崩溃、阻塞、数据丢失或明显卡顿均为不通过。

### 5.4 交互、文案与个性化体验

- 用户在各主要页面都能清楚知道“当前状态、下一步、保存是否成功、数据意味着什么”。
- 文案友好、简短、非评判；放纵餐与体重波动不使用惩罚、羞辱、恐吓或绝对化措辞。
- 根据用户的目标、完成度、记录频率和数据变化提供不同的反馈语境；不假设每个用户的性格、动机、健康状况和减脂节奏相同。
- 个性化仅作用于展示和鼓励，不虚构健康建议；用户可修改档案、目标和录入数据。
- 关键操作的触控区域足够大，文本对比度、层级和错误提示在户外/低亮度条件下仍可辨识。

### 5.5 数据安全、隐私与可维护性

- 云数据库与存储规则经过验证，用户只能访问自己的档案、记录和图片。
- 图片、头像、年龄、性别、身高体重等敏感信息的收集目的与使用范围在隐私说明中清楚告知。
- 客户端不暴露密钥、管理员权限或他人数据；日志不记录敏感原始内容。
- 代码按页面、组件、服务、常量、类型和样式清晰组织；重复逻辑抽离，关键算法与云权限有说明。
- 本计划、资产清单、数据结构和验收结果同步维护，使后续修改可追溯。

## 6. 完成定义

只有当所有核心流程在真机、弱网及空数据场景下通过，所有发布阻断级问题为零，视觉资产逐张通过检查，隐私与权限验证完成，并且第 5 节的验收项有可复核记录时，项目才可认定为达到可交付标准。

## 1.1 设计资产审计（2026-09-01）

已核对 `design/` 使用说明和元素位置清单：共有 43 个 PNG，覆盖首页、记录、数据、我的和海报五类界面。全部文件的画布均为 **1152 × 2048**，元素坐标保留在完整页面画布中；页面底色已替换为白色且**不是透明底**，文字、图标、演示体重/BMI/日期等均已烘焙在图内。

这意味着拆分包的正确用途是视觉参考、间距/坐标标尺和原型验收对照，**不得直接作为生产环境的响应式页面组件**：否则会出现白底遮挡、动态数据无法替换、放大模糊和异形屏适配失真。生产实现必须以原生小程序组件重建卡片、文字、图标、图表和导航；仅在可独立裁切、无动态文字、具备足够清晰度并完成视觉质检时，才允许抽取其中的静态装饰元素。

当前工作区未发现 `UI ref/` 文件夹。因此高保真整页原图尚不可核对；待该目录补充后，必须逐页将实现与原图进行视觉回归，更新页面映射和资产缺口清单。

## 1.2 审计修正与工程基线（2026-09-01）

经进一步核对，高保真原型实际位于 `UI-ref/`（连字符，不是 `UI ref/`）：`home_preview.png`、`p2_records.png`、`p2_records_v2.png`、`p2_records_v3.png`、`p3_data.png`、`p4_profile.png`、`p5_poster.png`。第 1.1 节中“未发现 `UI ref/`”仅指该精确目录名；现予以修正。后续视觉回归以 `UI-ref/` 的整页原图及经确认的记录页版本为准。

当前小程序工程为微信默认模板：仅有 `pages/index` 和 `pages/logs`，`app.json` 仅注册这两页，未配置云开发、业务 TabBar、数据页或健康记录能力。任何业务页面、云函数和数据模型均尚未创建。本阶段将保留该基线作为后续实现与验收的起点，且不以默认模板代码作为产品实现复用依据。
